# Navreo Learning Loop: Data-Recording Install Plan (FINAL, panel-approved)

Panel verification: 5 independent expert reviews per round (AI product, ML science, data engineering, GTM operations, AI governance), 3 rounds, 15 reviews total. Round 3 collective score: 8.0/10, unanimous 8s. The M9 comms context layer was then added at the operator's request and re-verified by a focused 3-expert delta panel (governance, product, data engineering) over 2 rounds, passing at 8.0/10 unanimous. All "raise to 9" fixes from the passing rounds are folded into this final version.

## 1. Objective and framing

Long-term goal (verbatim from the operator): "A platform that builds accurate prospect lists, ideates high-converting offers, drafts short, concise and relevant copy, responds to campaign data to optimise campaigns with the goal of driving more meetings, can self-respond to inbound messages to a level akin to an expert appointment setter, and do this all automatically with minimal human input besides top-line strategy."

This plan's scope is deliberately limited to the FOUNDATION: install the recording mechanisms that make self-learning possible, plus a weekly review routine that turns the records into insights and PROPOSED changes. Nothing in this build applies optimisations automatically. Every proposed change waits for explicit human approval. Record first, learn second, act third (act = later phase, out of scope).

Each target capability maps to a data stream that must be recorded:

| Capability | What must be recorded |
|---|---|
| Accurate prospect lists | Which list sources, briefs and lead scores actually convert downstream, cost-weighted |
| High-converting offers | Which offer variants (hard/soft, per variant, not per campaign) drive positives and meetings |
| Short relevant copy | Which hook frameworks, lengths and variants win, per lead actually sent, with stats that survive Smartlead's variant-stat resets |
| Respond to campaign data | What changes were made, by whom, why, and what happened after, measured against a plan fixed BEFORE the change |
| Self-respond to inbound | How replies are handled today: latency, content, responder, draft-vs-sent diffs, outcome, plus a rubric-based human quality signal |
| Drive meetings | The north-star outcome (booked AND held AND qualified, captured independently, reconciled) joined back to every upstream choice |
| Understand context | Team + client comms (Fathom transcripts incl. Google Meet calls, Slack across every channel) mirrored and distilled into structured context events (provider deaths, deliverability incidents, client decisions, strategy changes) that explain anomalies and feed confounder checks |

## 2. Existing infrastructure (verified against live schema, 2026-07-11)

Supabase project (fnykldftbkrccihdjayl) already records: contact_history (1.11M rows), replies (18.2k), sent_messages (6.1k outbound archive), campaigns (778) + campaign_versions (1,005), heyreach_campaigns/stats/conversations/leads, mailbox_stats_daily (26.5k), provider_usage ledger, enrichments, lists + list_rows (205k), people (568k), companies (294k), app_activity_log, list_upload_qa_runs + qa_gate_runs, suppressions (73k), clients (12). Daily Smartlead and HeyReach syncs are live; a reply categoriser labels inbound replies with a corrections table; manual triage tags are authoritative by policy.

Conclusion: raw activity capture largely exists. The missing pieces are the LEARNING layer: choice metadata, reset-proof and per-lead-attributable performance records, the meetings/outcome spine, a cross-user change ledger, inbound-handling annotations, pipeline self-monitoring, and the weekly review flywheel.

## 3. New mechanisms to install (M0-M9)

All new tables are additive, declare explicit primary keys and upsert semantics (safe to re-run any stage), and are service-role-only under RLS. Every sync/merge stage consults `suppressions` BEFORE insert (write-time enforcement with tombstones), so idempotent re-runs can never resurrect purged PII.

### M0 (cross-cutting). person_identities resolution spec
- `person_identities` mapping table: person_id (FK to the existing people table where resolvable, else minted), canonicalised email(s), canonicalised LinkedIn URL, resolution_method, resolved_at. Canonicalisation rules published (lowercase, strip plus-tags and trailing slashes, linkedin.com/in/ normalisation).
- Resolution runs inside each sync stage as rows land; unresolved touches keep their raw key and are marked unresolved (never dropped, never guessed). Join-coverage % is an M8 nightly metric. Every cross-channel join in this plan goes through this table.
- Backfill at install: seeded from the existing 568k people + 1.11M contact_history rows (a pure local join, no API cost).

### M1. campaign_meta + variant_registry (choice metadata)
- `campaign_meta` (PK campaign_platform_id): client, platform, mechanism (targeted-list / hiring-signal / engagement-signal / followers / events / lookalike / news), default_offer_type, lead_magnet, icp_brief, list_source (ocean / prospeo / ai-ark / theirstack / trigify / client-supplied), geo, created_by.
- `variant_registry` (PK variant_uid = platform + campaign + step + template_hash + revision_seq): variant label demoted to an attribute; hook_framework_id (Hook Framework Library); offer_type PER VARIANT (hard / soft, since mirrored hard+soft offers run inside one campaign); template_hash (sha256 of copy AFTER stripping merge tags and normalising spintax, per a published normalisation spec); word_count; subject_len; created_by; validity interval (created_at, superseded_at); parent_hash lineage. An in-place copy edit closes the old row's validity interval and registers a new revision: history never splits and never collides.
- Backfill at install: all currently-active campaigns tagged (LLM proposes classifications from stored sequences + briefs; HUMAN CONFIRMATION mandatory in both Training-Mode states). Historical copy from campaign_versions is hashed into variant_registry with validity intervals so the leaderboard does not start cold. New campaigns are tagged at build time by one instrumentation step in the campaign-build skills; a nightly orphan detector (M8) catches campaigns created outside the skills.

### M2. Per-variant and per-lead performance capture (reset-proof, attributable)
- `variant_stats_daily` (PK snapshot_date + platform + campaign_id + variant_uid, upsert): raw cumulative counters AS REPORTED, plus computed daily deltas with explicit boundary rules: day-0 rows are baseline-only (delta NULL, excluded from grading); reset detection (delta = max(0, today - yesterday), reset events flagged); on a reset day the delta is apportioned via campaign-level daily stats (which do not reset) or the variant-day is marked untrusted. Per-variant daily exposure counts stored. Opens recorded but flagged untrusted. HeyReach equivalents included.
- `lead_variant_assignments` (PK platform + campaign_id + lead_id + step): resolved TEMPORALLY at sync time: each sent message's sequence/variant identifier is joined against the registry row whose validity interval contains the message's sent_at, so a message sent under old copy is never attributed to a later edit. HeyReach: where the API does not expose per-lead variant identity, LinkedIn copy attribution is EXPLICITLY DESCOPED to campaign+step level and recorded as such (no false precision).
- Concurrent-exposure rule: within-campaign variant contrasts are valid ("gold") ONLY on concurrent-exposure cohorts (same campaign, same step, sends inside overlapping validity intervals); non-overlapping contrasts are automatically demoted to observational.
- Backfill at install: a bounded replay of the sent_messages archive into lead_variant_assignments where message-history data allows, so review #1 opens with populated attribution.
- Install: bounded additional stages of the existing daily syncs (200 req/min respected), failure-isolated so a new-stage failure can never abort or corrupt pre-existing stages.

### M3. decision_ledger + sequence_structure (cross-platform, cross-user change capture)
- `decision_ledger`: one row per material change (PK deterministic idempotency key: hash of platform + campaign + change_type + observed diff + effective date): ts, actor (Bjion / Asad / Yasir / skill-name / unattributed-ui), platform, campaign_id, change_type, rationale (free text or proposal_id), before/after diff reference. Feeds: (1) skill instrumentation via one shared helper in navreo_db.py; (2) daily settings + sequence snapshot-diff (extends campaign_versions), attributed `unattributed-ui` when no actor is exposed; (3) existing app_activity_log federated via a view.
- `sequence_structure` (written by the same snapshot-diff feed, one row per campaign version): step count, per-step delay days, threading mode (thread-reply vs new-subject), subsequence flags. Follow-up cadence produces 40-60% of replies in real programs; this makes it a queryable, learnable dimension (graded at cumulative altitude).

### M4. meetings (the outcome spine: staged, idempotent, reconciled, qualified)
- `meeting_events` staging table (PK source_platform + source_event_id, upsert): every raw booked/held signal lands here first. First-class booked source: the calendar/booking layer (Google Calendar events via the connected calendar, and booking-link webhooks where available); Smartlead Meeting-request / Call-booked tags and HeyReach conversation outcomes are corroboration; daily Fathom poll supplies held signals; manual entries allowed.
- `meetings` materialised by a provably deterministic, re-runnable merge job: cluster by earliest qualifying event per (person_id, client), fixed 72h window anchored to that event, stable tie-break on (source_platform, source_event_id); person_id falls back to canonicalised raw attendee email when unresolved. Reschedule policy: a new booked_at more than 72h after the cluster anchor creates a new meeting row, linked rescheduled_from when a reschedule signal exists.
- Fields: person_id, raw attendee email, client, attributed campaign_id, source_platform, booked_at, held_status (held-confirmed / unknown / no-show), qualified flag (qualified / unqualified / unset, set in the weekly correction line, ~30s per meeting), fathom_recording_id, join_confidence, attribution_rule_version.
- held_status is tri-state: Fathom recording = held-confirmed; absence = UNKNOWN, never no-show; no-show only ever set manually. Cumulative meetings cuts grade on QUALIFIED-held, so tire-kicker volume cannot game the north star.
- Attribution rule v1 (deterministic, versioned, recorded on-row): anchor on the reply thread that produced the booking when one exists; fall back to most recent outbound touch across email + LinkedIn within 30 days before booked_at; documented tie-break. Low-confidence joins queue into the weekly manual-correction line.
- Reconciliation (M8-checked): every Fathom-held recording must match a booked-side row within the merge window or fire a "missing booked feed" alert; booked-feed coverage % reported weekly. Quarterly audit: 30-50 sampled attributions stratified across ALL join_confidence levels, precision recorded per attribution_rule_version.
- Backfill at install: meeting_events seeded from historical Fathom meetings + existing Call-booked tags.

### M5. inbound_handling_log (appointment-setter corpus)
- A VIEW over data already stored (replies + sent_messages + categoriser labels) plus an annotation table: reply_id, received_at, first_response_at (latency), responder (team member or AI-drafted), response message ref, category, categoriser_version, correction_status, thread outcome (meeting_id / dead / handed-off), full thread reference.
- Preference-pair capture: whenever a response was AI-drafted or template-based, the draft AND the final sent message are both stored, so human edits become draft->final diffs: the richest training signal available for the future responder.
- Quality signal: each weekly review samples handled replies STRATIFIED by category and outcome, rated on a 3-item rubric (correct next action / tone / accuracy) with a duplicate item for rater consistency. Sample size 10 (drops to 5 with fortnightly duplicate item if the human budget binds).
- Categoriser accuracy watch: a monthly stratified human re-label of raw replies (including uncategorised/negative buckets), tracked as precision/recall per categoriser_version in review Section 0, with a degradation threshold that flags positive-rate claims exactly as the deliverability rule flags domain-health breaches.
- Corpus governance: suppressed/unsubscribed leads excluded at write time and purged on suppression; raw bodies retained 24 months rolling (aggregates indefinitely); any future model-training use of reply bodies requires a separate explicit approval (recorded).

### M6. proposals + weekly_reviews (the flywheel: pre-registered, DB-enforced, lifecycle-managed)
- `proposals`: proposal_id, created_by_review, claim, evidence (query + numbers), proposed_change (exact, actionable), MANDATORY pre-registered measurement plan fixed at creation: metric, exact before/after windows, minimum sample, expected effect size, known confounders. status (awaiting / approved / rejected / applied / stale), approved_by, approved_at, approval_evidence, applied_at, decision_ledger ref, measured_outcome.
- DB-enforced gate: a trigger rejects any status transition to approved/applied unless approved_by AND approval_evidence are non-null; the UPDATE is permitted only to a named approver role whose credential is HUMAN-HELD ONLY (transition performed by the operator in the Supabase dashboard under their own login; the credential never appears in any agent-readable file). approval_evidence is a machine-checkable artifact reference (a Notion comment ID on the review page, verified to exist by the next review). Every transition logs to decision_ledger.
- Application protocol: approved proposals are applied only by a human or a human-invoked skill, which must write the decision_ledger row carrying the proposal_id BEFORE status may move to applied (enforced in the same trigger). This prevents approved-but-applied-differently drift.
- Measurement integrity: measured_outcome computed ONLY against the pre-registered plan, on clean windows (other ledger changes inside the window flag it confounded; untouched sibling campaigns recorded as pseudo-controls). Evidence hierarchy: concurrent-exposure within-campaign contrasts first; cross-campaign template_hash pooling always labelled observational. Copy proposals are framed "add new variant alongside incumbent", never edit-in-place, so future measurements are randomized A/Bs by construction.
- Lifecycle: proposals older than 3 weeks auto-expire to `stale` (retained as signal; "human said no" is signal too). Section 0 shows the awaiting count. The weekly human ask is budgeted honestly at 30 minutes (approvals + context-event confirm/dismiss + qualified flags + corrections + ratings); when the cap binds, the stated triage order cuts in this sequence: approvals-backlog nagging first, then meeting corrections, then rubric ratings, then event confirmations last (confirmations feed THIS week's decisions, so they outrank ratings, which feed a future phase).
- `weekly_reviews`: review_id, period, notion_url, headline metrics snapshot, data_quality_status (ok / degraded).

### M7. Weekly Learning Review routine (local, scheduled, dead-man protected)
- A local scheduled task (Mondays 07:00 Europe/London), per the operator's explicit request for a local routine. Reads ONLY Supabase, computes the review, publishes a Notion page under a new "Weekly Learning Reviews" parent, updates proposals, notifies.
- Freshness preflight FIRST: every source must have a successful sync run < 36h old and pass row-delta sanity checks (including variant-counter monotonicity/reset checks). On failure: publish a "DEGRADED DATA - no proposals issued" page and suppress proposal generation entirely.
- Transactionally re-runnable: all DB writes in one transaction keyed on the review period; the Notion page is overwrite-idempotent; a crash mid-run cannot leave a half-complete review that passes the dead-man check.
- Dead-man's switch: a pg_cron job checks Monday 12:00 for the period's weekly_reviews row and alerts if missing.
- Technical enforcement of record-only: the review job runs on a dedicated Supabase role that is read-only everywhere except INSERT on proposals/weekly_reviews, holds no Smartlead/HeyReach write credentials, and uses a DEDICATED Notion integration token shared exclusively with the "Weekly Learning Reviews" parent page. It never applies changes; the page always ends with "Proposed changes (awaiting approval)".

### M8. Pipeline health (the recording layer watches itself)
- `sync_runs` ledger: stage, watermark, rows written, status, error, duration; every stage (existing and new) writes a row.
- Nightly checks: last-success per stage (alert > 48h stale); % of active campaigns with campaign_meta rows (orphan detector); % of sent leads with variant assignments; person-identity join coverage; meetings join-confidence mix; Fathom-vs-booked reconciliation; suppression-purge verification across ALL new PII-bearing tables (meetings raw emails, lead_variant_assignments, person_identities, M5 annotations); integrity check that the proposals trigger and role grants are unchanged.
- Phase-2 readiness gates, stated as numbers and verified in the weekly review before any auto-apply phase may even be proposed: campaign_meta coverage >= 95% of active campaigns; variant-assignment coverage >= 90% of sent leads on Smartlead (HeyReach at its descoped altitude); high-confidence meeting joins >= 80%; booked-feed coverage >= 85%; attribution precision audit with 90% binomial CI lower bound >= 85%; 4 consecutive non-degraded weekly reviews.
- M9 additions to the nightly checks: comms-feed staleness (Fathom poll, per-channel Slack watermark), channel coverage (channels ingested vs the channel roster, so a new client channel cannot be silently missed), extraction backlog (transcripts/messages awaiting the context-event pass) with a backfill burn-down target date, entity-resolution coverage on context_events, confirm-queue backlog, and purge verification over the three comms tables.

### M9. Comms context layer (Fathom + Slack: the "why" behind the numbers)
Purpose: campaign data says WHAT happened; team and client comms say WHY. A provider going out of business, a deliverability incident, a client pausing outreach, a strategy pivot agreed on a call: these explain anomalies that would otherwise be misread as copy or list failures. This layer records the comms and distils them into structured events the review must consult before flagging anomalies or proposing changes.

- `comms_transcripts` (PK fathom_recording_id, upsert): title, started_at, attendees (resolved to team members and, via attendee email domains, to the clients table), meeting_kind (client-call / internal), Fathom summary, full transcript text, ingested_at. Fed by the SAME daily Fathom poll M4 already runs (one poll, two consumers: held-status and transcript capture). Google Meet calls are covered because Fathom records them; meetings Fathom did not record are simply absent (no false completeness claims).
- `slack_messages` (PK channel_id + message_ts, upsert): channel_name, author, text, thread_ts, permalink, edited_at, deleted_at, ingested_at. Ingestion is watermark + trailing re-scan, not a pure high-watermark: each daily run pulls new messages per channel AND re-pulls the trailing 7 days (the upsert PK makes this idempotent), which captures edits inside the window. Thread replies (where client decisions and escalations actually live) are captured by an explicit open-threads pass: any thread_ts with activity in the trailing 30 days is held in a bounded open-threads set and polled via conversations.replies from its latest_reply watermark on a decaying budget; replies landing on threads older than that horizon are documented as lost, not silently implied captured. Tombstoning is guarded: it runs ONLY after a fully-paginated, successful channel-window scan (a truncated or crashed scan never tombstones), the upsert self-heals (a reappearing message clears deleted_at and restores text), and an M8 alert fires on any abnormal tombstone rate. Tombstones propagate a source_removed flag to citing context_events; meaningful edits propagate a source_edited flag symmetrically. Content older than the re-scan window is point-in-time by documented policy. Roster: ALL public channels + every client channel, refreshed each run; channels ADDED to the roster are surfaced as an acknowledge line in review Section 0 (no silent auto-enrol into warehousing + LLM processing). Private channels and DMs are EXCLUDED by default (operator can opt specific private channels in). Rate limits stated honestly: Slack's conversations.history tier for non-Marketplace apps can be as low as ~1 request/min at 15 messages/page, so the 12-month backfill runs as a slow bounded burn-down over days-to-weeks with an M8-tracked target date; the crawl runs on the proven pg_cron -> pg_net -> Render worker pattern (a multi-hour burn-down cannot live inside an edge-function stage), while the daily incremental fits comfortably.
- `context_events` (PK event_id): event_date span (start/end, max-span capped), event_type (provider-shutdown / provider-incident / deliverability-incident / client-pause / client-escalation / strategy-decision / offer-change / icp-change / team-decision / other), entities RESOLVED AT WRITE TIME (client refs against the clients table, providers against a small provider enum, domains canonicalised M0-style; unresolved entities kept raw and flagged, resolution coverage an M8 nightly metric), one-line summary, confidence, source_type (fathom / slack), source_refs, extracted_by (model + version), review_status enum (pending / confirmed / dismissed) + reviewed_by/reviewed_at, source_removed (bool), source_edited (bool).
- Deterministic dedupe (specified as an algorithm, not a fuzzy hash): candidates are processed in stable (source, ts) order; a new candidate MERGES into an existing OPEN event when the canonical resolved entity IDs and event_type match and its date falls within 3 days of the event's current span (extending the span up to the cap); otherwise it opens a new event. One provider incident discussed across five Slack messages and two calls lands as ONE event with multiple source refs; a multi-week incident extends one event's span instead of fragmenting. Candidates with unresolved entities go to the confirm queue UNMERGED rather than corrupting the match key.
- Extraction: a daily bounded LLM pass over ONLY new-or-edited transcripts/messages. Idempotent by construction: a `comms_extraction_runs` ledger keyed (source_ref, content_hash, extractor_version), written transactionally with the proposed events, means re-runs and crashes never re-propose processed items, while a meaningful edit (new content_hash) re-extracts and flags citing events source_edited. The extraction endpoint is NAMED AND BOUND: the Anthropic API under zero-data-retention, no-training commercial terms; raw comms text leaves Supabase ONLY to that endpoint and to no other surface. A monthly extraction-precision audit (small stratified sample re-checked per extractor_version, including the dismissal rate and a sample of CONFIRMED events, mirroring the M5 categoriser watch) keeps both the extractor and the rubber-stamp risk honest.
- Citation gate (hard rule): ONLY review_status=confirmed events may be cited as anomaly explanations or listed in a proposal's known-confounders. Pending or dismissed events, at ANY model confidence, render as "candidate (unconfirmed)" and can never redirect or suppress a proposal. Confirmations are informed and revocable: the source excerpt is shown inline at confirm time, and a confirmed event can be corrected or un-confirmed later with the change logged to decision_ledger. Latency is managed: a short Friday private digest of high-confidence candidates precedes the Monday review so same-week context is citable, and any proposal whose entity has a PENDING high-confidence candidate in its +/-14-day window is flagged "pending-context" on the review page (visible to the approver, who can hold it 48h for confirmation). The confirm/dismiss queue is delivered to the operator's PRIVATE surface (never the shared Notion page), hard-capped at 15 events/week (overflow held, backlog tracked in M8).
- Anomaly-explanation rule (baked into review code): before the review flags any anomaly (reply-rate drop, bounce spike, positive-rate shift), it queries CONFIRMED context_events in a +/-14-day window for matching entities and cites them alongside the anomaly; candidates are listed separately as unconfirmed. An anomaly with a confirmed external cause generates a context-aware proposal (e.g. "pause and re-route domains", not "rewrite the copy").
- Backfill at install: full available Fathom history; Slack history per rostered channel bounded to the trailing 12 months, burned down at the rate-limited pace above. Backfill extraction runs in a one-time batch-review mode: only high-confidence historical candidates are surfaced, in one sitting, so review #1's confirm queue is not flooded.
- Governance (stricter than the campaign tables, since this is internal + client-sensitive speech): service-role-only tables, with the raw-text boundary enforced AT THE GRANT LAYER: the weekly-review role is denied SELECT on comms_transcripts.full_transcript and slack_messages.text (it reads a metadata + context_events view only); only the extraction role reads full text, and these grants join the M8 nightly integrity check. Raw transcript/message text NEVER appears on any Notion page (only one-line CONFIRMED event summaries with source links back to Fathom/Slack; unconfirmed candidates never appear on the shared page). The comms corpus is NOT part of the M5 training corpus and any model-training use requires its own separate recorded approval. 24-month rolling retention on raw text. Purge paths are BOTH client-keyed AND team-member-keyed; on a deletion request, raw comms rows are deleted and confirmed context_events are retained only with entity refs anonymised AND the free-text summary scrubbed/regenerated (the action recorded). The M8 nightly purge verification explicitly covers comms_transcripts, slack_messages and context_events. DM exclusion is the default and any widening is an explicit operator decision. Transparency: a one-time internal notice to the team, and a line in client onboarding, state what is mirrored, the retention window, and purge rights.
- Out of scope for v1, by design: Gmail ingestion (campaign email is already archived via sent_messages/replies; the personal Gmail inbox can be added later with the same watermark pattern if wanted); Notion content (already accessible in place; not mirrored).

## 4. Weekly Review page spec (Notion)

0. Pipeline health: per-feed freshness, rows vs expected, orphan campaigns, join coverage, categoriser precision/recall per version, awaiting-proposal count, human-minutes budget status, trigger/role integrity. DEGRADED banner + no proposals if preflight failed.
1. Deliverability health: per-domain bounce and reply trends vs fleet baseline, provider split, warmup/blocked flags from mailbox_stats_daily; inbox-placement tests FORTNIGHTLY per sending-domain cohort, landing in a table the confounder rule reads. The confounder rule runs before ANY copy/mechanism claim: sends from unhealthy domains are excluded or flagged, so a burned domain can never masquerade as "copy stopped working".
2. Context this week: CONFIRMED context events (provider incidents, client decisions, strategy changes) from M9, one line each with source links. Unconfirmed candidates never appear here; they go to the operator's private confirm/dismiss queue (capped at 15/week). Every anomaly flagged anywhere in the review cites matching confirmed context events (+/-14 days) before any copy/list/mechanism theory is offered.
3. TL;DR: meetings booked, held-confirmed and qualified-held this week vs trailing 4-week average, per client.
4. Funnel by platform: sends -> replies -> positives -> meetings, email vs LinkedIn.
5. What is working: positive rate (weekly decision metric) cut by mechanism, offer_type (variant-level), hook_framework_id, list_source, cadence (cumulative altitude). Cumulative cell-level counts with Benjamini-Hochberg correction; minimum-sample gates (200 sends and 5 positives per cell); anything not surviving is "directional". Concurrent-exposure within-campaign contrasts cited first; pooled cuts labelled observational. Meetings grade cumulatively (trailing 8-12 weeks) on qualified-held at mechanism/offer altitude. Per-client positive -> meeting conversion recorded so proposals state expected MEETINGS.
6. Copy leaderboard: top and bottom variants by template_hash, graded to replies weekly and qualified-held meetings cumulatively via lead_variant_assignments; concurrent-exposure contrasts flagged as gold evidence.
7. Inbound handling: median first-response latency, reply -> meeting conversion by responder, draft->final edit-distance trend for AI-drafted responses, the stratified rubric sample.
8. List quality calibration: upload-gate scores and lead-score verdicts vs realised outcomes, plus cost-per-positive and cost-per-meeting by list_source from provider_usage.
9. Last week's approved proposals: measured strictly against pre-registered plans, honest nulls and confounded flags included.
10. Proposed changes (awaiting approval): proposal_id, evidence, expected effect, exact change, pre-registered measurement plan; copy proposals framed add-variant-alongside-incumbent; relevant context events listed in known-confounders.

Analytical guardrails baked into review code: reply categories never compared one-category-across-periods; corrections applied before any positive count; manual triage tags authoritative; opens never evidential.

PII rule for Notion: aggregates and internal IDs only; no lead emails, names or reply text on any Notion page; correction prompts reference meeting IDs. Comms rule: raw transcript/Slack text never appears on Notion; only one-line confirmed event summaries with source links.

## 5. Governance and safety

- Record-only mandate enforced technically: role separation, scoped Notion token, DB trigger on approval transitions, human-held approver credential, nightly trigger/grant integrity check.
- Human approval gate with audit trail: approved_by + approval_evidence required at database level; approver credential never agent-readable; transitions logged; application requires a linked decision_ledger row first.
- Additive and reversible: new tables only; sync extensions append-only and failure-isolated; both scheduled jobs deletable in one command each.
- Mandatory human confirmation (mode-independent) for the campaign_meta LLM backfill.
- Data hygiene fix included, GATED ON APPROVAL: enable RLS with service-role-only policies on the 3 existing exposed tables (sent_messages, reply_category_corrections, optimiser_notifications).
- PII: stays in the existing private Supabase project; no new third-party services; 24-month rolling retention on raw bodies; suppression enforced at write time (tombstones) AND verified nightly; purge propagates to every new PII-bearing table including person_identities.
- Comms governance (M9): raw transcripts and Slack text are service-role-only and leave Supabase ONLY to the named extraction endpoint (Anthropic API under zero-data-retention, no-training terms) and to no other surface; Notion gets one-line CONFIRMED event summaries with source links, nothing more; private channels and DMs excluded by default, widened only by explicit operator decision; the comms corpus is excluded from the M5 training corpus and any model-training use requires its own separate recorded approval; purge paths client-keyed AND team-member-keyed, with in-Slack deletions honoured via tombstoning; on client deletion, confirmed events survive only with anonymised entity refs (recorded); 24-month rolling retention on raw comms text; nightly purge verification covers all three comms tables.

## 7. Known limitations (stated up front)

- Actor attribution: Smartlead exposes no per-user audit trail; UI changes are diff-detected and attributed `unattributed-ui`. Mitigation: Claude-side changes fully attributed; light team convention for manual edits.
- Meeting joins: personal/calendar emails will sometimes defeat resolution. Mitigation: join_confidence + weekly correction line + quarterly stratified precision audit; booked and held captured independently; unknown never coerced to no-show.
- HeyReach variant attribution: descoped to campaign+step where the API does not expose per-lead variant identity; recorded at its true altitude, never faked.
- Small samples: weekly decisions run on positives; meetings-level claims are cumulative at higher altitude on qualified-held; the review says "insufficient evidence" honestly.
- Pre/post measurement is not a randomised experiment; confounded windows flagged, pseudo-controls used where available, concurrent-exposure contrasts preferred, causal certainty never overstated.
- Comms coverage is honest, not total: meetings Fathom did not record are absent; Slack DMs and private channels are excluded by default; Slack content older than the trailing re-scan window is point-in-time; Gmail is deferred (campaign email is already archived). Context events are LLM-proposed but citable ONLY once human-confirmed, so extraction errors degrade to "unexplained anomaly, candidate pending", never to a false explanation; a monthly extraction-precision audit backs this up.
- The first review opens with backfilled history (variant registry, attribution replay, meetings seed, 12 months of Slack + full Fathom history) rather than cold, but fresh-signal density still compounds from week 3-4.

## 8. Rollout

Single session (roughly half a day, plus the comms backfill running in the background) with Loop Training Mode ON, so every step is approved before it runs. Estimated: ~15 new tables + 2 views + 2 roles + 1 trigger + 2 scheduled jobs (local weekly review, pg_cron dead-man check); comms ingest and context extraction run as bounded stages of the existing daily cadence. No new external services; the only new spend is the small daily LLM extraction pass over new comms.
